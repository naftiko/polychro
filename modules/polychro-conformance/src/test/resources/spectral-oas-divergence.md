# `spectral:oas` divergence — rules not yet ported to `polychro:openapi`

Tracks the gap between Spectral's built-in `spectral:oas` ruleset and Polychro's bundled
`polychro:openapi` equivalent, as resolved by `extends: spectral:oas` (naftiko/polychro#84).
This is the **input scope for Phase 4** (naftiko/polychro#85 — `$ref` resolution and deep
`then.field` support, both required by several rules below).

`@stoplight/spectral-rulesets/dist/oas/index.js` (pinned version, see this module's
`target/spectral-harness/`) against
`modules/polychro-rulesets/src/main/resources/rulesets/openapi.yml`. Regenerate by re-running
the same diff if either ruleset changes — do not hand-maintain by inspection:


## Naming note — `openapi-paths-kebab-case`

Ported as the flagship consumer of the JSONPath key-selector operator (`~`, naftiko/polychro#83)
targeting `$.paths.*~` (the path *keys*, not their values). `spectral:oas` has no rule under
this exact name; the closest conceptual sibling is `path-keys-no-trailing-slash` (listed below,
a distinct check). Not a divergence to close — an intentionally Polychro-authored addition.

## Not yet covered (39)

Grouped by why they are out of scope today, per naftiko/polychro#85's stated dependencies.

### Requires `$ref` resolution (naftiko/polychro#85)
Rules that inspect resolved schema/parameter/response/example objects across `$ref`
boundaries — Polychro's JSONPath evaluator does not follow `$ref` today.
- `oas2-unused-definition` — unused `definitions` entries (needs whole-document `$ref` graph).
- `oas3-unused-component` — unused `components.*` entries (same reason, OAS3 side).
- `oas2-valid-schema-example` / `oas3-valid-schema-example` — validates `example` against the
  (possibly `$ref`'d) `schema`.
- `oas2-valid-media-example` / `oas3-valid-media-example` — same, for media-type-level examples.
- `oas3-examples-value-or-externalValue` — `examples.*` objects are frequently `$ref`'d.
- `oas3-callbacks-in-callbacks` — needs to walk `$ref`'d `callbacks` transitively.
- `duplicated-entry-in-enum` — needs the resolved `enum` array, whichever schema it lives on.

### Requires deep `then.field` / alias composition (naftiko/polychro#85)
Rules whose Spectral `given`/`then.field` targets a nested property path deeper than
Polychro's current single-level `field` support, or that need the alias/`given` composition
(`PathItem`/`OperationObject`/`ResponseObject`/`LinkObject` — see `spectral:oas`'s own
`aliases:` block) that Polychro's ruleset model does not yet express.
- `operation-success-response` — needs the `OperationObject`/`ResponseObject` alias chain.
- `operation-operationId` / `operation-operationId-unique` / `operation-operationId-valid-in-url`
  — need the `OperationObject` alias (uniqueness additionally needs a document-wide collection).
- `operation-parameters` / `oas2-parameter-description` / `oas3-parameter-description` — needs
  the `OperationObject` alias and per-parameter nested traversal.
- `oas2-operation-formData-consume-check` — needs the `OperationObject` alias plus a correlated
  check between `parameters[*].in` and the operation's `consumes`.
- `operation-tag-defined` — needs a cross-document reference from `#OperationObject.tags[*]`
  back to the top-level `tags[*].name` list.
- `operation-tags` / `operation-singular-tag` — same alias dependency.
- `operation-description` — needs the `OperationObject` alias.
- `path-params` — needs correlated traversal of path templates and their declared `parameters`.
- `oas2-discriminator` / `oas2-schema` / `oas3-schema` — deep schema-object structural rules
  (`discriminator`, `type`/`properties` consistency) needing recursive schema traversal.
- `oas2-anyOf` / `oas2-oneOf` — OAS2 forbids `anyOf`/`oneOf` anywhere in a schema; needs the
  same recursive schema-object walk as `array-items`/`typed-enum` below.
- `typed-enum` — needs the resolved `type` + `enum` pair on the same (possibly `$ref`'d) schema.
- `array-items` — needs `type: array` schemas found anywhere in the document (alias
  `ArrayProperties`, a `$..[?(...)]` recursive-descent filter Polychro's JSONPath subset does
  not yet evaluate).
- `contact-properties` — needs conditional validation across multiple `info.contact.*` fields.
- `oas3-server-variables` — needs correlated traversal of `servers[*].url` templates against
  `servers[*].variables`.
- `oas2-operation-security-defined` / `oas3-operation-security-defined` — needs a cross-document
  reference from `security[*]` (op- or root-level) back to `securityDefinitions`/
  `components.securitySchemes`.

Rules that likely need no new engine capability, just ruleset authoring — smaller, mechanical

`spectral:oas` can be ported in one pass instead of piecemeal.

## Closing this file

When a rule above is ported to `polychro:openapi`, remove it from its section here and add a
corresponding conformance fixture under `modules/polychro-conformance/src/test/resources/fixtures/`
(see `openapi-full-ruleset/` for the pattern). This file is considered closed (deletable) once
all 39 rules have moved to `polychro:openapi` — flag to the user before deleting, per this
repo's "deletion is human-only" convention (`agents-shared/context/engineering.md`).
